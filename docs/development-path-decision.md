# 智能体开发路径决策

日期：2026-09-23  
官方依据：`https://wt.ioa.pub/docs.html`

## 官方当前提供的路径

官方指南把使用方式分为三类，其中真正的开发路线有两条：

1. 使用已有智能体：从首页或叮当中发现和调用，不属于创建作品。
2. ACPs SDK：自行实现智能体服务和 ACS，在 Registry 注册审核，获得 AIC 后使用
   `acps-cli` 获取 EAB 并申请 mTLS 证书。
3. WIT：使用梧桐智能体开发框架编写和运行智能体，框架内置处理部分注册接入流程。

Flux（`https://wt.ioa.pub/flux/login`）当前页面定位是 WIT 框架门户，提供 wheel 下载和
文档入口。现有证据不支持把它描述成拖拽式、免代码的在线智能体创建器。

## 路线比较

| 维度 | ACPs SDK | WIT |
|---|---|---|
| 控制力 | 高，协议、状态机、服务和证书流程可显式控制 | 较高层，框架封装更多 |
| 起步速度 | 较慢 | 较快 |
| 自研代码可见度 | 高，适合技术报告与答辩举证 | 业务代码可见，但框架实现以发行包提供 |
| 注册与证书 | 手工走 Registry、AIC、EAB、mTLS | 框架内置部分接入流程 |
| 当前验证状态 | Direct RPC 已在本项目跑通 | 安装和官方预检已通过，最小 Agent 尚未运行 |
| 主要风险 | 接入步骤多、部署要求更高 | 过度依赖封装可能削弱技术创新表达 |

## 当前决策

采用“SDK 主线、WIT 备线”：

- 参赛核心 Leader/Partner、业务编排、状态与证据链优先用 SDK 显式实现。
- WIT 用于快速验证 Agent runtime、自动生成 ACS 和框架接入能力；不把 WIT 本身包装成
  团队自研技术。
- 在核心业务闭环稳定前，不同时维护两套等价实现，避免浪费赛前时间。
- 如后续 Registry、证书或部署时间成为主要风险，再评估将非核心 Partner 切换到 WIT。

## 官方顺序

SDK 路线的官方顺序为：

`实现服务并准备 ACS → Registry 注册并提交审核 → 获得 AIC → 获取 EAB → 申请 mTLS
证书 → 配置服务 → Discovery/Registry 验证`。
